# Let's Master Control Hub — 관제 대시보드 기획안

작성일: 2026-11-18  
범위: `pyw31337/lets` 중앙 관제 허브. `Let's Insu (렛츠인슈)`, `Let's Law (렛츠로)`, `Let's People (렛츠피플)`, `Let's Asset (렛츠에셋)`, `Let's Art (렛츠아트)`는 초기에는 수집 현황과 최소 기능만 유지하고, 개별 서비스 브랜딩·OG·아이콘 고도화는 원장 수집 이후로 미룬다.

## 1. 조사 결과와 현재 상태

현재 단일 스냅샷은 `data/master_ecosystem_pulse.json`이다. 스냅샷에는 서비스 15개, 자동화 장치 19개, 누적 색인 4,710,073건, 설정상 일일 수집 44,983건, 일일 분석 2,253건, 품질 점수 99.3이 기록되어 있다.

그러나 관제 화면을 신뢰 가능한 운영판으로 사용하기 전에 다음 문제를 먼저 해결해야 한다.

1. `summary.total_automation_devices`는 19와 일치하지만, README와 인수인계 문서에는 24·28대가 혼재한다.
2. 서비스 원장(`standalone_services`)과 장치 원장(`automation_devices`)의 누적 수치가 동일한 기준인지 보장되지 않는다. 예: People 서비스 172,312명과 People 수집기 128,600명이 서로 다른데 기준·시점·중복 제거 상태가 표시되지 않는다.
3. `scripts/daily_ecosystem_aggregator.py`는 현재 각 서비스의 설정된 `daily_ingest_rate`를 누적하는 방식이다. 실제 수집 결과, HTTP 응답, 저장된 원장 변화량과 분리되지 않으므로 `planned_rate`와 `observed_delta`를 구분하지 않으면 허위 진행률이 된다.
4. 실행별 시작·종료시각, 재시도 횟수, 실패 원인, 원천별 확보율, 저장 바이트, 큐 길이, 실제 분석 처리량이 공통 스키마로 남지 않는다.
5. 19개 장치에는 Day/Month/Year 시계열이 일부 존재하지만, 모든 장치가 같은 단위·시간대·집계 규칙을 사용한다는 보장이 없다.

따라서 첫 화면을 화려하게 만드는 것보다 먼저 **계획량(planned), 관측량(observed), 검증량(verified), 공개량(published)**을 분리해야 한다.

## 2. 자동화 장치 분류

현재 스냅샷의 19개 장치는 다음 네 단계로 관리한다.

| 단계 | 장치 수 | 역할 |
|---|---:|---|
| INGEST | 13 | 뉴스·인물·법률·보험·기업·예술·시장·교통·문화 원장 수집 |
| ANALYZE | 4 | 온톨로지 관계, 케미스트리, 금융 스트레스, 교통 사고 분석 |
| QUALITY | 1 | 영상망 센티널 및 이상징후 감시 |
| OBSERVE/STREAM | 1 | 실시간 서비스 스트림(헤어·구매·지하철·뉴스 등)의 운영 상태 |

각 장치는 반드시 다음 정보를 갖는다.

- 장치 ID, 서비스 ID, 단계, 담당 저장소
- 원천 URL/API와 인증 상태
- 수집 대상과 단위
- cron 및 시간대
- 계획량과 실제량
- 성공·실패·재시도·지연시간
- raw/clean/derived/published 출력 경로
- 마지막 성공 시각과 데이터 신선도
- 중복 제거율·근거 첨부율·누락률
- 다음 실행 예상 시각

## 3. 권장 화면 구조

### A. 상단 운영 요약

카드 4개만 사용한다.

1. 현재 정상 장치 / 전체 장치
2. 최근 24시간 실제 수집량
3. 최근 24시간 실제 분석량
4. 가장 오래된 미갱신 원장

각 숫자는 계획량 대비 실제량, 전일 대비 증감, 마지막 성공 시각을 함께 보여준다.

### B. 기간 전환

`Day · Month · Year` 세그먼트 하나를 사용한다.

- Day: 최근 14일, 시간대별 실행량·지연·실패
- Month: 최근 12개월, 월별 원장 증가량·분석량·품질점수
- Year: 연도별 누적량·목표 달성률·확장 이력

기간을 바꾸면 모든 차트가 같은 축 규칙으로 바뀌며, 서비스·단계·장치 필터는 유지한다.

### C. 서비스별 흐름 보드

각 서비스는 박스 안에 박스를 중첩하지 않고 한 줄의 흐름으로 표현한다.

`수집 → 정제 → 분석 → 품질 → 공개`

각 단계 아래에 실제량, 품질, 지연시간을 놓고, 구간을 누르면 우측 상세 패널에서 해당 장치 목록과 원천별 증거를 보여준다.

### D. 처리량·기울기 차트

- 막대: 실제 처리량
- 실선: 7일 이동평균
- 얇은 점선: 계획량
- 색상: 정상(파랑), 가속(초록), 둔화(주황), 정체/실패(빨강)
- 호버/터치: 날짜, 계획량, 실제량, 달성률, 실패 수, 주요 원천, 샘플 링크

모바일에서는 차트를 가로 스크롤시키지 않고, 기간을 7개 지점으로 줄이거나 세로 요약표로 전환한다.

### E. 품질 상승 흐름

`Raw → Clean → Analyzed → Verified → Published`의 수평 퍼널을 사용한다.

각 단계에는 다음을 표시한다.

- 레코드 수
- 탈락 수와 탈락 이유
- 근거 첨부율
- 중복 제거율
- 이미지/인물 매칭 정확도
- 시간 필드 확보율

### F. 이상징후와 운영 로그

오른쪽 고정 패널 대신 본문 하단의 접을 수 있는 “주의 로그”로 배치한다.

- ZERO_DROP
- FLAT_CURVE
- FRESHNESS_LAG
- SOURCE_AUTH_FAILURE
- DUPLICATE_SPIKE
- QUALITY_REGRESSION

각 항목은 원인, 영향 범위, 마지막 재시도, 다음 자동 조치, 관련 실행 링크를 제공한다.

## 4. 상호작용 규칙

- 모든 차트 포인트는 마우스 오버와 터치 탭을 모두 지원한다.
- 툴팁은 화면에 이미 있는 숫자를 반복하지 않고, 원천·실행 ID·오류·샘플 링크를 우선 보여준다.
- 장치명·서비스명·원천명은 탐색 가능한 링크로 만든다.
- 실패 항목은 “다시 실행”보다 먼저 “왜 실패했는지”를 보여준다.
- 키보드 포커스와 44px 이상의 조작 영역을 보장한다.
- `prefers-reduced-motion`에서는 차트 진입 애니메이션을 끈다.

## 5. 데이터 계약

각 실행은 다음 이벤트를 남긴다.

```json
{
  "run_id": "people_global_crawler:2026-11-18T05:00:00+09:00",
  "device_id": "people_global_crawler",
  "service_id": "people",
  "stage": "INGEST",
  "planned": {"count": 245, "unit": "person"},
  "observed": {"count": 238, "unit": "person", "bytes": 1820440},
  "verified": {"count": 231, "duplicate_removed": 7, "evidence_rate": 0.94},
  "published": {"count": 231, "path": "data/people/..."},
  "started_at": "2026-11-18T05:00:03+09:00",
  "finished_at": "2026-11-18T05:14:22+09:00",
  "status": "SUCCESS",
  "retry_count": 0,
  "source_health": [{"source": "Wikidata", "status": "OK", "latency_ms": 420}]
}
```

현재 aggregator는 이 계약을 읽어 집계해야 하며, 설정값만 더해 실제 수집량처럼 표시해서는 안 된다.

## 6. 시안 방향

### 권장안: “운영 흐름 + 원장 탐색”

- 밝은 회색 바탕
- 넓은 섹션 간격
- 진한 제목과 작은 보조 설명
- 색상은 상태와 서비스 식별에만 사용
- 테두리보다 얇은 구분선과 약한 배경 차등 사용
- 첫 화면에는 요약·흐름·기울기만 노출
- 상세 원장·실행 로그는 탭 또는 하단 드로어로 지연 노출

Supabase의 페이지 컨테이너·페이지 섹션·차트 패턴처럼 화면 폭을 콘텐츠 밀도에 따라 선택하고, 토스식으로 핵심 수치와 변화량을 짧게 전달한다. 공통 간격·색·반응형 규칙은 Lets Design System v1.1.0을 유지한다.

## 7. 구현 순서

### 1단계 — 사실성 정리

- 19개 장치와 문서의 24·28대 표기를 정합화
- 서비스 원장과 장치 원장의 기준일·중복 제거 규칙 명시
- 계획량과 실제량 분리
- 실행 이벤트 저장소 추가

### 2단계 — 관제 데이터 어댑터

- 각 서비스의 상태 파일을 공통 이벤트로 변환
- 없는 값은 0이나 100으로 채우지 않고 `unknown`으로 표시
- 자동 집계가 실제 산출물의 해시와 행 수를 검증

### 3단계 — 디자인 시안

- 권장안 화면을 실제 데이터로 렌더링
- Day/Month/Year, 서비스, 단계 필터를 연결
- 320px·768px·1440px 시각 검수

### 4단계 — 운영 전환

- GitHub Actions에서 매일 집계
- 이상징후 발생 시 알림
- 주간 목표 대비 보고서 생성
- 에이전트 인수인계 문서에 실행 ID와 커밋 기록

## 8. 승인 전 보류 항목

아직 확정하지 않은 것은 화면 코드와 서비스별 고유 브랜딩이다. 이 문서의 데이터 계약과 권장안이 승인된 후에 `/lets` 화면을 실제 개편한다. InSu·Law·People·Asset·Art의 개별 서비스 페이지는 당분간 수집 현황·최소 기능만 유지한다.
